# Plan Crutches: план реалізації

Plan Crutches — це мод (плагін із function hooks) для Claude Code. Він перехоплює момент, коли Claude завершує план у plan mode, і відкриває панель рев'ю в desktop-додатку. Користувач бачить структуру змін, коментує, малює архітектуру і натискає Submit. Мод перетворює коментарі на промпт із правками або затверджує план.

## 1. Ключові архітектурні рішення

### 1.1. Форма: мод плюс окрема веб-сторінка (рішення змінено 2026-10-14)

Мод малює панель (`Pane`) прямо в Claude desktop через хук `ui.render`. Причини:

- Хук `tool.call` перехоплює `ExitPlanMode`, тобто момент готовності плану, без зовнішніх мостів.
- Мод має `$.model.complete` і `$.model.fork` для генерації реалізацій і відповідей на питання тим самим клієнтом і кредами, що й сесія.
- Мод має `$.fs` для читання файлів проєкту і файлу плану, `$.ui.selection()` для виділеного тексту, `$.prompt.submit` для запуску наступного ходу.
- Не потрібен локальний сервер, порт, WebSocket і синхронізація двох процесів.

Обмеження: панель будується з фіксованого набору елементів. На desktop це `Box`, `Text`, `Button`, `Input`, `Select`, `Link`, `Code`, `Markdown`, `Svg` і `Client`. `Client` — це власний модуль моду, який малює тими ж елементами, але отримує події вказівника (`onPointer`) і клавіш (`onKey`). Саме `Client` + `Svg` дають редактор діаграм.

Після перших тестів панелі користувач попросив повноцінний JS і стилі, тому головним інтерфейсом стала окрема сторінка (етап 8 реалізовано). Мод залишається мостом: перехоплює `ExitPlanMode`, тримає стан, викликає модель, пише MD-запис. Панель залишається другим, скороченим видом із посиланням на сторінку.

Схема сторінки:

- `server/index.mjs` — Node-сервер без залежностей на `127.0.0.1` (порт з опції `port`, типово 4817, зайнятий порт замінюється вільним). Роздає `web/`, тримає знімок стану, віддає його сторінці через SSE (`/api/events`), приймає дії сторінки (`POST /api/action`) і пише кожну дію JSON-рядком у stdout. Кожен запит до API несе токен, який мод створює раз на сесію.
- Мод запускає сервер через `$.process.spawn`, читає його stdout (рядок `listening` з портом, далі `action`), і після кожної зміни стану надсилає повний знімок `POST /api/state` через `$.http.fetch`. Раз на хвилину пінгує сервер; сервер сам завершується без контакту 10 хвилин.
- Відкриття сторінки: опція `openIn` — `auto` пробує browser pane desktop-додатку через `$.mcp.call('Claude_Browser', 'navigate')`, далі системний браузер (`open`/`xdg-open`/`cmd start`); `system`; `none`.
- `web/` — ванільні ES-модулі без збірки: `app.js` (стан, рендер, попап коментаря до виділеного тексту), `tree.js`, `codeview.js` + `highlight.js` (лістинг і diff з номерами рядків), `markdown.js`, `diagram.js` (SVG-редактор: блоки, стрілки, олівець, текст, експорт SVG), `i18n.js`, `api.js`. Кольори в `theme.css` (світла й темна), власні правки в `web/custom.css`.
- `hooks/web.ts` — чиста частина мосту: розбір дій, побудова знімка, протокол stdout.

### 1.2. Протокол структурованого плану

План Claude — це Markdown у файлі плану. Для дерева файлів і сигнатур потрібна структура. Рішення: мод додає до системного промпту секцію (хук `prompt.compose`, scope `session`), яка в plan mode вимагає дописати в кінець файлу плану fenced-блок `plan-crutches` із JSON такої форми:

```json
{
  "summary": "Markdown. Короткий опис змін, до ~9000 символів.",
  "files": [
    {
      "path": "src/auth/session.ts",
      "status": "new | modified | deleted",
      "description": "Що і навіщо змінюється в цьому файлі.",
      "symbols": [
        {
          "name": "refreshSession",
          "kind": "function | method | class | type | const",
          "signature": "export async function refreshSession(id: string): Promise<Session>",
          "description": "Що робить. Без реалізації.",
          "anchor": "після createSession"
        }
      ]
    }
  ]
}
```

Папки виводяться з шляхів. Папка позначається новою, якщо всі файли в ній нові. Запасний шлях: якщо блоку немає або він не парситься, мод витягує структуру з Markdown одним викликом `$.model.complete` із суворою JSON-схемою.

### 1.3. Цикл рев'ю без блокування хука

Бюджет одного хука — 10 секунд власного часу. Чекати на рішення користувача всередині перехопленого `ExitPlanMode` не можна. Тому цикл такий:

1. Хук `prompt.attachment` з матчером `{ type: 'plan_mode' }` зберігає `e.detail.planFilePath` у `$.state`.
2. Хук `tool.call` на `ExitPlanMode` читає файл плану, парсить блок, зберігає модель плану у `$.state`, відкриває панель (`$.ui.open({ id: 'plan-review', focus: true })`) і відповідає `{ deny: 'План відкрито на рев'ю в панелі Plan Review. Зупинись і чекай: рішення користувача прийде наступним повідомленням.' }`. Claude завершує хід.
3. Користувач працює в панелі. Усі коментарі, діаграма і згенеровані тіла методів живуть у `$.state`.
4. Натискання Submit:
   - Є коментарі: мод складає промпт із правками (шлях, символ, рядки, текст коментаря, діаграма як текст) і викликає `$.prompt.submit({ text, asUser: true })`. Claude оновлює файл плану і знову викликає `ExitPlanMode`. Хук перечитує файл, панель показує версію 2 і позначає коментарі як опрацьовані.
   - Коментарів немає: мод ставить статус `approved` у `$.state` і сабмітить «План затверджено, переходь до виконання». Наступний `ExitPlanMode` хук пропускає через `next(e)`. Вбудований діалог підтвердження плану при цьому залишається: документація API каже, що `tool.check` з `allow` не закриває діалог, який потребує людини. Користувач натискає «Yes» один раз і обирає режим виконання. Якщо користувач натисне «No», мод повертає статус `reviewing`, і наступний `ExitPlanMode` знову проходить через панель.
5. Хук `prompt.attachment` з `{ type: 'plan_mode_exit' }` скидає стан рев'ю і закриває панель.

Хук `tool.call` отримує `.catch`, який за замовчуванням пропускає виклик далі (`next.called ? next(e) : next(e)`), щоб збій моду ніколи не блокував Claude.

### 1.4. Блок задачі

Панель починається з блоку «Задача»: сирий текст задачі. Джерела, за пріоритетом:

1. Результат Jira-інструмента. Хук `tool.call` з матчером на `jira_get_issue` або `getJiraIssue` чекає `next(e)` і зберігає текст результату і ключ задачі в `$.state.task.jira`.
2. Поле `task` у блоці `plan-crutches`, яке Claude заповнює дослівно.
3. Останній промпт користувача перед входом у plan mode. Хук `prompt.submit` зберігає кожен промпт людини, хук `prompt.attachment` для `plan_mode` фіксує його як текст задачі, коли інший ще не захоплений.

Блок згортається кнопкою і показує джерело (Jira з ключем або «так, як подав користувач»).

### 1.5. Запис плану в MD-файл

Кожен план, що пройшов через панель, записується у проєкт як Markdown: `docs/plans/<дата>-<ключ-jira>-<slug-назви>.md`. Папка задається опцією `plansDir`. Файл перезаписується цілком на кожну подію: нова версія плану, новий коментар, Submit, затвердження, вихід із plan mode. Вміст: статус і версія, шлях до файлу плану Claude, блок задачі, опис, список змін із сигнатурами, коментарі по версіях із позначками «надіслано» і «опрацьовано у vN», діаграма як текстовий граф, попередження парсера, історія подій. Демо-режим (`/plan-review demo`) файл не пише.

### 1.6. Стан

Увесь стан панелі лежить у `$.state` під іменем моду, з контрактом у `types/index.d.ts`:

- `plan`: розпарсена модель плану, версія, шлях до файлу, статус (`reviewing | revising | approved | idle`).
- `ui`: розгорнуті папки, вибраний файл, вибраний символ, активна вкладка.
- `comments`: список `{ id, target: { path, symbol?, lines? }, text, resolvedInVersion? }`.
- `canvas`: вузли, ребра, вільні лінії, підписи.
- `bodies`: згенеровані реалізації за ключем `path#symbol`, зі статусом `loading | ready | failed`.
- `qa`: історія питань і відповідей.

`$.store` використовується лише для кешу `bodies` між сесіями (необов'язково).

## 2. Структура моду

```
plan-crutches/
  .claude-plugin/plugin.json      name, version, description, types
  hooks/hooks.json                { "modules": ["./register.tsx"] }
  hooks/register.tsx              реєстрація хуків, оркестрація циклу рев'ю
  hooks/plan-parser.ts            пошук і парсинг блоку plan-crutches, fallback через модель
  hooks/tree.ts                   побудова дерева папок із списку файлів, позначки new/modified/deleted
  hooks/prompts.ts                тексти: секція системного промпту, промпт правок, промпт генерації тіла
  hooks/pane.tsx                  ui.render для Pane: header, дерево, деталі файлу, опис, Q&A
  hooks/canvas.tsx                Client-модуль: редактор діаграм на Svg + onPointer
  hooks/*.test.ts                 тести через claude plugin test
  types/index.d.ts                контракт PluginState
  README.md                       встановлення, протокол, обмеження
  .claude-plugin/marketplace.json для /plugin install (етап 7)
```

Розробка йде в `~/.claude/dev-mods/<session>/plan-crutches/` з hot reload. Фінальна копія живе в цьому репозиторії.

## 3. Етапи

### Етап 0. Каркас і середовище

- Створити три файли моду і контракт типів. Запустити `claude plugin validate` і `tsc -p`.
- Увімкнути hot reload у сесії.
- Зареєструвати команду `/plan-review`, яка відкриває панель із фікстурою (готовий JSON плану). Так панель розробляється без реального plan mode.
- Звірити версії. CLI `claude` зараз 2.1.204, desktop використовує 2.1.295. API модів змінюється між релізами. Оновити CLI до версії desktop перед `claude plugin test`.

Результат: порожня панель відкривається командою, валідатор і типи зелені.

### Етап 1. Протокол плану і перехоплення ExitPlanMode

- Хук `prompt.compose`: секція з вимогою блоку `plan-crutches` і описом протоколу рев'ю.
- Хук `prompt.attachment` для `plan_mode`, `plan_mode_exit`: збереження шляху плану, скидання стану.
- Хук `tool.call` для `ExitPlanMode`: читання файлу, парсинг, відкриття панелі, `deny` із поясненням, пропуск при `approved`.
- Хук `tool.check` для `ExitPlanMode`: `allow` при `approved`.
- `plan-parser.ts` з fallback через `$.model.complete`.
- Тести: парсер на трьох фікстурах (валідний блок, зламаний блок, без блоку), deny і пропуск.

Результат: у реальному plan mode панель відкривається з розібраним планом, Claude зупиняється і чекає.

### Етап 2. Панель: header, дерево змін, опис

- Header: назва плану, версія, лічильник коментарів, кнопка Submit (`variant="primary"`).
- Дерево папок і файлів. Усе розгорнуте за замовчуванням. Кожен рядок — одна `Button` з назвою, позначкою `new`, `mod`, `del` і лічильником коментарів. Клік на папку згортає або розгортає. Клік на файл відкриває деталі.
- Коментар до папки чи файлу: кнопка «Коментар» біля вибраного рядка відкриває `Input`, Enter зберігає. Список коментарів під рядком.
- Блок опису: `Markdown` із `summary`. Ліміт близько 9000 символів (три сторінки). Понад ліміт — кнопка «Показати все».
- Вкладки панелі: «Зміни», «Діаграма», «Запитати».

Результат: план із фікстури читається і коментується.

### Етап 3. Деталі файлу, сигнатури, генерація реалізації

- Вигляд файлу: опис змін, список символів. Кожна сигнатура — `Code` з мовою за розширенням. Коментар до символу тією ж механікою, що й до файлу.
- Для `modified` файлів мод читає поточний вміст через `$.fs.read` і показує заглушковий unified diff: контекст із файлу, `+` рядки із сигнатурами і коментарем «що робить». Малюється через `Code format="diff"`.
- Кнопка «Розгорнути реалізацію» біля символу. Мод викликає `$.model.complete({ model: 'haiku', effort: 'low', maxTokens: 2000 })` із контекстом: `summary`, опис файлу, поточний вміст файлу (обрізаний), сигнатура, опис символу. Результат кешується в `$.state.bodies`. Поки триває запит, рядок показує «генерую». Повторний клік згортає. Кнопка «Перегенерувати» скидає кеш.
- Коментар до виділеного коду: блоки коду малює `Client`-модуль `select.tsx`. Користувач протягує мишкою по рядках, рядки підсвічуються, над виділенням з'являється спливаюче поле з `Input`, Enter зберігає коментар із діапазоном рядків і текстом виділення (модуль надсилає його хукам через `post`, хук `ui.message` додає коментар). Якщо поверхня не підтримує `Client` (`ui.fault`), мод повертається до звичайного `Code` і кнопки «Коментар до виділеного», яка читає `$.ui.selection()`.
- Згенероване тіло не йде у промпт правок як код. У промпт потрапляє лише факт і текст коментаря до нього.

Результат: по кожному файлу видно сигнатури і diff, тіла довантажуються на клік, коментарі прив'язуються до коду.

### Етап 4. Редактор діаграм

- `canvas.tsx` як `Client`-модуль. Інструменти: прямокутник, стрілка, підпис, вільна лінія, стирач, очистити.
- Малювання через `onPointer` (`down`, `move`, `up`). Координати в клітинках; `fine` на desktop може бути відсутнім, тому крок сітки дорівнює клітинці.
- Рендер у `Svg` з `isInteractive: false`. Підпис вводиться через `Input` під полотном.
- Стан полотна локальний у модулі, після кожної зміни `post` у хук, хук пише в `$.state.canvas`.
- Серіалізація для промпту: список вузлів з назвами і список ребер «A → B: підпис». SVG додається у `~/.claude/plan-crutches/<plan>-diagram.svg` і згадується в промпті шляхом.

Результат: користувач малює схему, Claude отримує її як текстовий граф.

### Етап 5. Запитати Claude про зміни

- Вкладка «Запитати»: `Input` і історія.
- Відповідь через `$.model.fork({ prompt })`. Fork працює поверх транскрипту сесії, тож Claude уже знає план і проєкт. У промпт додається вибраний файл і символ як фокус.
- Відповідь малюється `Markdown`. Показується витрачений контекст (`usage`).
- Кнопка «Зробити коментарем» переносить питання і відповідь у коментарі до вибраної цілі.

Результат: питання не ламають головну розмову і не змінюють план.

### Етап 6. Submit і цикл правок

- Збирання промпту правок у `prompts.ts`: заголовок із версією плану, коментарі згруповані по файлах, для кожного ціль (шлях, символ, рядки або виділення) і текст, далі діаграма як граф, далі інструкція «онови файл плану і знову виклич ExitPlanMode».
- Після сабміту статус `revising`, панель показує «Claude переробляє план». Кнопка Submit заблокована.
- На наступному `ExitPlanMode` мод перечитує план, піднімає версію, позначає всі надіслані коментарі `resolvedInVersion`. Користувач бачить, що змінилося: файли, які з'явилися або зникли, підсвічені.
- Затвердження без коментарів: `approved`, `tool.check` allow, виконання.
- `plan_mode_exit` закриває панель і очищує стан.

Результат: повний цикл «план → рев'ю → правки → план v2 → затвердження → виконання» працює в реальній сесії.

### Етап 7. Якість і дистрибуція

- Тести `claude plugin test`: парсер, дерево, збирання промпту, deny і allow, рендер панелі на `desktop` і `terminal` з фікстурою.
- Прогін на окремому тестовому репозиторії з трьома сценаріями: новий модуль, зміна існуючого файлу, видалення.
- README: встановлення, протокол, обмеження, скріншоти.
- `marketplace.json` і команда `/plugin install plan-crutches --marketplace <owner>/<repo>`.

### Етап 8. Веб-сторінка рев'ю (виконано)

Окрема сторінка з повноцінним JS замість панелі як головного інтерфейсу: див. 1.1. Без Vite і залежностей, сервер на вбудованому `node:http`, обмін через SSE і stdout дочірнього процесу. Перевірка: `node --test tests/server.node.mjs` для сервера, `tests/web.test.ts` для мосту, `node scripts/demo-server.mjs` для ручного огляду сторінки в браузері.

## 4. Ризики і відкриті питання

- Вбудований діалог підтвердження `ExitPlanMode` залишається після затвердження в панелі: типи API прямо кажуть, що `allow` з хука не закриває діалог, який потребує людини. Це один клік «Yes», і він же вибирає режим виконання.
- Дисципліна Claude щодо блоку `plan-crutches`. Секція системного промпту плюс fallback через модель мають покривати більшість випадків. Якість fallback-парсингу перевіряється на етапі 1.
- `$.ui.selection()` на desktop. Документація каже, що відповідь — виділення в сторінці хоста. Чи потрапляє туди виділення в панелі, перевіряється на етапі 3.
- Точність вказівника на desktop. Без `fine` координати йдуть у клітинках. Для схем із прямокутників і стрілок цього достатньо.
- Ліміти дерева: 100 000 символів тексту на одне малювання і 100 000 символів у `props` `Client`. Великий план показує лише розгорнуті частини, тіла методів — лише розгорнуті.
- API модів позначено як early access і змінюється між релізами. Типи перегенеровуються при оновленні, код звіряється з ними.
- Версія CLI 2.1.204 проти desktop 2.1.295. `claude plugin test` і `validate` для function hooks потребують версії desktop.

## 5. Підтверджені рішення

1. Форма: мод із панеллю в desktop.
2. Модель для генерації тіл методів і для витягування структури з Markdown: `sonnet` (опція `model`).
3. Мова панелі: англійська і українська, перемикач у хедері, типова мова в опції `language`.
4. Ліміт блоку опису: 9000 символів (опція `summaryLimit`).
5. Блок із сирим текстом задачі на початку панелі (розділ 1.4).
6. План фіксується в MD-файлі у проєкті (розділ 1.5).

## 6. Стан реалізації

Зроблено в першому проході (етапи 0, 1, 2, більша частина 3, 5 і 6):

- Каркас моду: маніфест з опціями, контракт стану, `claude plugin validate` і `tsc` без помилок.
